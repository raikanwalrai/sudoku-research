\section{Purpose}

This document records the implementation history, methodological decisions,
experimental results, reproducibility information, and research conclusions
for the Sudoku neural-to-fundamental-function research project.

\section{Research Principle}

Sudoku is used as a controlled combinatorial reasoning laboratory. The
research does not claim to resolve the P versus NP problem. Instead, it
investigates whether progressively sophisticated neural architectures can
learn and expose compact structural representations of Sudoku constraints
and whether such learned structure can ultimately be converted into an
independent non-neural function or solver.

The pre-push gate executes five checks:

\begin{enumerate}

    \item working-tree security scan;
    \item staged-content security scan;
    \item current \texttt{HEAD} security scan; and
    \item repository-history security scan.
\end{enumerate}

The scanner checks configured credential-bearing filenames and secret
patterns covering AWS credentials, GitHub tokens, OpenAI-style API keys,

assignments, password assignments, and database URLs containing embedded

The security gate is therefore treated as a mandatory repository

ensure that the Git hook does not depend on an activated virtual
environment. The scanner uses an available Python interpreter, defaulting
to \texttt{python3} when no explicit \texttt{PYTHON\_BIN} is supplied.

The security scanner is pattern-based and is not a mathematical or
cryptographic guarantee that every possible secret will be detected.
Its purpose is to provide a reproducible repository-hygiene control and

\section{Sprint 01}

Sprint 01 established the mathematical representation and foundational
constraint-validation layer for Sudoku.

\subsection{Implementation}

The board is represented as a $9\times9$ structure with integer cell values in
the domain $\{0,\ldots,9\}$. The value $0$ represents an empty cell. A
row-major flattened representation contains exactly 81 cells.

The implementation provides an immutable \texttt{Board} abstraction with:

\begin{itemize}
    \item construction from rows;
    \item construction from exactly 81 row-major values;
    \item conversion back to row and flattened representations;
    \item coordinate-based cell access;
    \item functional cell replacement returning a new board;
    \item completeness checking;
    \item validation of board shape and cell-value domain.
\end{itemize}

Boolean values are explicitly rejected even though Python treats
\texttt{bool} as a subclass of \texttt{int}. This preserves the intended
mathematical cell domain.

\subsection{Constraint Validation}

The validator is separated from the board representation. It provides:

\begin{itemize}
    \item partial-board validation;
    \item row constraint validation;
    \item column constraint validation;
    \item $3\times3$ box constraint validation;
    \item complete-solution validation;
    \item legal candidate-value computation for empty cells.
\end{itemize}

A valid partial board contains no duplicate non-zero values in any row,
column, or $3\times3$ box. A valid solution additionally requires every cell
to be populated.

\section{Sprint 02}

Sprint 02 established the deterministic exact Sudoku solver and
ground-truth oracle required for all subsequent learning experiments.

\subsection{Solver Design}

The exact solver operates directly on the immutable \texttt{Board}
representation established in Sprint 01. Sudoku constraint semantics are
delegated to the existing validator rather than duplicated inside the
solver.

The search procedure uses deterministic depth-first backtracking with
Minimum Remaining Values (MRV) cell selection. Candidate values are
obtained from the Sprint 01 candidate computation. Candidate traversal is
sorted so that identical input boards produce identical search decisions
and solutions.

\subsection{Oracle Semantics}

The solver provides three principal operations:

\begin{itemize}
    \item \texttt{solve(board)} returns a solution only when exactly one
    solution exists;
    \item \texttt{count\_solutions(board, limit)} counts solutions up to
    the supplied stopping limit;
    \item \texttt{has\_unique\_solution(board)} tests whether exactly one
    solution exists.
\end{itemize}

With the standard stopping threshold of two, the oracle distinguishes:

\[
\operatorname{count}(X)=0
\]

for an unsatisfiable puzzle,

\[
\operatorname{count}(X)=1
\]

for a uniquely solvable puzzle, and

\[
\operatorname{count}(X)\geq2
\]

for a puzzle with multiple solutions.

This distinction is important because later synthetic datasets must be
able to guarantee unique solutions without relying on a neural model.

\subsection{Solution Verification}

The implementation also provides \texttt{verify\_solution(board, solution)}.
A verified solution must be complete, satisfy all Sudoku constraints, and
preserve every non-zero clue present in the original puzzle.

\subsection{Research Independence}

The exact solver contains no neural-network component and does not depend
on learned parameters, learned representations, or training data. It is
therefore maintained as an independent computational oracle against which
later neural models can be evaluated.

The intended later comparison is:

\[
N_{\theta}(X) \stackrel{?}{=} G(X),
\]

where $N_{\theta}$ denotes a neural model and $G$ denotes the exact
ground-truth solver.

\subsection{Verification}

\section{Sprint 03 --- Synthetic Sudoku Generator}

\subsection{Research Objective}

Sprint 03 establishes the synthetic data-generation layer for the Sudoku
reasoning laboratory. The purpose is to generate reproducible puzzle and
solution pairs without relying on external Sudoku datasets.

A generated instance is represented as
\[
(X,S),
\]
where \(S\) is a complete valid \(9\times9\) Sudoku solution and \(X\) is a
partial board obtained from \(S\) by controlled clue removal.

\subsection{Generation Contract}

For every generated pair \((X,S)\), the following invariants are required:

\begin{enumerate}
    \item \(S\) is a valid complete Sudoku solution;
    \item \(X\) is a valid partial Sudoku;
    \item every non-zero value in \(X\) is identical to the corresponding
    value in \(S\);
    \item
    \[
    \operatorname{count\_solutions}(X,2)=1;
    \]
    \item
    \[
    \operatorname{solve}(X)=S;
    \]
    \item generation is reproducible from an explicit random seed and
    generation parameters; and
    \item the generated instances originate entirely from the synthetic
    generator rather than an external Sudoku corpus.
\end{enumerate}

The solution generator uses randomized deterministic backtracking driven by
Python's standard-library \texttt{random.Random(seed)}. This separates
controlled stochastic variation in data generation from the deterministic
Sprint-02 exact solver used as the ground-truth oracle.

\subsection{Controlled Clue Removal}

Given a complete solution \(S\), cells are considered for removal in a
seed-controlled order. A candidate removal is retained only when the
resulting puzzle remains uniquely solvable. The uniqueness criterion is
evaluated using the Sprint-02 solution-counting oracle with a cap of two
solutions.

Thus, a generated puzzle is accepted only when
\[
\operatorname{count\_solutions}(X,2)=1.
\]

The resulting solution must additionally satisfy
\[
\operatorname{solve}(X)=S,
\]
providing an explicit consistency check between the generated target and
the independent oracle.


\subsection{Empirical Boundary Validation}

The initial greedy clue-removal implementation was empirically evaluated
before being accepted as the Sprint-03 generator. Five seeds were tested at
each of 60, 40, 30, 25, 20, and 17 retained clues. All five trials succeeded
at 60, 40, 30, and 25 clues. No trial succeeded at 20 or 17 clues.

A second diagnostic tested ten independent clue-removal orders for each of
five independently generated complete solutions at a target of 20 clues.
All 50 removal attempts failed to reach the target. The stopping points were
generally between 23 and 27 clues.

These observations indicate that simply increasing randomized restarts does
not provide a reliable solution to the sparse-puzzle generation problem.
The limitation is therefore treated as a property of the current greedy
removal strategy rather than as a seed-selection problem.

Accordingly, the validated operating range of the current Sprint-03
generator is restricted to
\[
25\leq k\leq81,
\]
where \(k\) is the requested retained clue count. Requests below 25 clues
are outside the supported operating range.

This restriction is an implementation boundary and not a mathematical claim
that uniquely solvable Sudoku puzzles with fewer than 25 clues do not exist.
A future sparse-puzzle generation methodology may use a fundamentally
different construction or search strategy. Such a methodology is outside
the current Sprint-03 implementation scope.

The negative boundary experiments are retained as research evidence because
they prevent an unsupported claim of sparse-puzzle generation capability.

\subsection{Experimental Scope}

Sprint 03 deliberately prioritizes reproducibility, validity, uniqueness,
and traceability over puzzle-difficulty optimization. Difficulty
stratification will be considered after the basic generator is validated.

Formal train/validation/test partitioning and leakage-prevention procedures
are deferred to Sprint 04 so that generation and dataset partitioning remain
separate experimental concerns.

Large generated datasets are excluded from version control by the
repository's existing data-directory policy. The research repository
therefore retains the generator implementation, tests, specifications, and
reproducibility information rather than large generated artifacts.
